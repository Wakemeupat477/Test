# Mail threads task

## Как запустить

```bash
cp .env.example .env
docker compose up worker
docker compose run --rm exporter
node selfcheck.js out/result.jsonl
```

При смене `CANDIDATE` сначала: `docker compose down -v`.

## Как устроено хранение и почему

SQLite хранится в именованном томе `mail-data`. `messages` содержит уникальные письма (`external_id` — PK), `message_links` — все `references` и `in_reply_to` в исходном порядке, `sync_state` — cursor/признак завершения, `schema_migrations` — версии миграций. Страница и следующий cursor фиксируются одной транзакцией, поэтому после остановки загрузка продолжается с checkpoint без дублей.

## Если появится второй почтовый сервис

Добавлю адаптер push-источника и поле источника; вместо внешнего message id понадобится стабильный внутренний ключ и дедупликация по данным события. Готовые разговоры можно сразу переводить во внутренние связи/идентификатор треда. База, финализация и exporter в основном сохранятся.

## Два worker над одной базой

Работа останется корректной. Миграции повторно проверяются под write-lock; `external_id` уникален, а сохранение страницы делает `BEGIN IMMEDIATE` и сверяет cursor после получения блокировки. Проигравший worker отбрасывает устаревшую страницу; цена — лишние запросы к provider.

## Можно ли выполнить шаг дважды

Изменения состояния идемпотентны: миграции версионированы, письма/ссылки вставляются без дублей, checkpoint двигается только из ожидаемого cursor, а `thread_key` и `parent_id` пересчитываются детерминированно. Повторный HTTP-запрос влияет только на метрики/rate limit provider.

## Что сознательно не усложнял

Не вводил ORM и очередь: для одного последовательного cursor API они не дают пользы. Компоненты связности считаются один раз после полной выгрузки через Union-Find; инкрементальная схема понадобилась бы для бесконечного потока.

## Что упрётся при x10 объёме

Сначала — финализация: все ID и связи загружаются в память, затем обновляются строки SQLite. При миллионах писем я бы считал компоненты батчами/во внешнем хранилище и делал массовые обновления; при нескольких writers ограничением станет и SQLite.
